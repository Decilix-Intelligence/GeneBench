# 卡 4.1：任务容器的隔离约束与出向策略

**执行面跑在 finance02 上。被测 agent 是不可信方。**
隔离必须由**宿主机侧**强制，不能依赖「容器内不去做」。

---

## 1. 文件系统隔离

| # | 约束 |
| --- | --- |
| FS-1 | 任务容器**不得 bind-mount 任何宿主机路径**。唯一例外是 runner 为该次任务创建的工作目录 —— 边界由 L-5a 给死：**挂载源与 run dir 精确相等**（卡 4.3 §12.1 TK-1） |
| FS-2 | 不得挂载任何 NFS |

**为什么 FS-1 比「不挂 NFS」更强（N-29）**：finance02 本地就有
`/data/market_lake_f02`（**40 GB，`drwxr-xr-x` world-readable**，45,661 文件、13,496 分区目录）。
容器只要挂了 `/data` 或其任何父路径就能**直读整个湖**，**根本不需要 NFS**。
这个坑很容易在写 compose 时无意踩到 —— 比如为了共享工作目录顺手挂了 `/data/shared`。

**验收（可测）**：
* FS-A：容器内 `ls /data` **必须失败**
* FS-B：容器内 `cat /proc/mounts` 里**不得出现**宿主机的 `/data`

---

## 2. 网络隔离

**文件系统干净不等于隔离成立。** f01 的 `6443`（kube-api）、`10250`（kubelet）、
`2049`（nfs）都对 LAN 开着；f02 本地也有数据服务。

| # | 约束 |
| --- | --- |
| NET-1 | 容器接入**自定义 compose 网络**，网段避开 `10.42/16`、`10.43/16`、`10.88/16` |
| NET-2 | 出向**默认拒绝**。白名单只有两个目标：**网关** `192.168.1.48:18080` 与**出向代理**（见第 3 节）|
| NET-3 | 出向白名单由**网络拓扑**保证（`internal: true` + 代理边车），**不用** `DOCKER-USER` 链 —— 见 §3.2 的改进说明。**不要依赖容器内不去连** —— 被测 agent 是不可信方 |
| NET-4 | 端口映射**一律显式**写 `192.168.1.219:PORT:PORT`，**禁止裸** `-p PORT:PORT` |

**NET-4 的理由（D-07）**：docker 的 `-p` 默认绑 `0.0.0.0`，
而且会**自插 `DOCKER` 链规则绕过 ufw** —— 比服务自己绑 `0.0.0.0` 更隐蔽。
而 tailscale 走 `ts-input` 链、同样绕过 ufw，tailnet 里有开发机。
**这条要做成 compose 文件的 lint 规则，不能只是笔记里的提醒。**

**验收（可测）**：
* NET-A：容器内连 `192.168.1.48:18080`（网关）**成功**
* NET-B：容器内连 `192.168.1.48:6443`（kube-api）**失败**
* NET-C：容器内连 `192.168.1.219` 上任意端口**失败**

## 3. 出向公网策略 —— **默认拒绝 + 受控代理 + 主机名/SNI 白名单**（2026-09-01 已批准）

### 3.1 决定性理由不是「防数据外传」，是「防经互联网前视」

被测 agent 需要调用自己的模型 API，所以完全断网不可行。
但**放开公网的真正代价不是数据外传，而是**：

> **我们整套 as-of 强制会当场失效。**
> 冻结线是 `2026-07-31`。一个在评测 2026 年 7 月的 agent，
> 只要能上公网，就可以直接查 2026 年 8 月发生了什么。

红线 7、冻结的 provider、网关的 `as_of` 判定、卡 5.1 的前视探针 ——
**这些全都只管住了「经我们的数据面前视」，管不住「经互联网前视」。**

而且它的失败形态又是 D-06 那个：**分数会静默地虚高，没有任何东西报错**。
网关 `access_log` 干干净净，探针全绿，因为 agent 根本没走我们的数据面。

**所以「默认拒绝」是必须的，不是可选的。**

### 3.2 方案：出向全部经受控代理，按**主机名 + TLS SNI** 过滤

```
gb_task (internal: true，**没有默认路由**)      gb_egress
   ┌──────────┐                        ┌───────────────┐
   │  task    │───▶ :18080 转发 ──────▶│ 网关 .48:18080 │
   │(不可信方) │───▶ :3128  CONNECT ──▶│  模型 API      │
   └──────────┘      egress-proxy      └───────────────┘
        其余一切目标：**没有路由可走**，不是「被规则挡住」
```

**对签字建议的一处改进（已批准）**：默认拒绝**不用** `DOCKER-USER` 链，改由**拓扑**保证。

* iptables 方案要 root，且在**宿主机**留持久状态 —— 一次 `iptables -F`、一次 docker 重启、
  另一个管理员的一条规则，白名单就没了；
* `internal: true` 的容器**根本没有出口**，**没有可被清空的状态**；
* 白名单因此是**代码**（`egress_proxy.MODEL_API_ALLOW`），进版本库、可审查、可测试。

* 代理边车同时接两网，是**唯一**出口；容器的 `HTTP(S)_PROXY` 指向它；
* 代理按 **`CONNECT` 目标主机名**过滤，并**校验 TLS SNI 与之逐字相等** ——
  否则可以 CONNECT 到白名单域名、TLS 里握另一个域名（domain fronting）；
* **白名单每一条必须指名「哪个被测配置需要它」**，没有引用者的条目就是死白名单面；
* 代理**全量记录**每一次出向请求，**拒绝也记**（不记等于没拦）。

### 3.3 为什么不用纯 iptables 的 IP 白名单

模型 API 在 CDN 后面，**IP 会轮转**。IP 白名单只有两种结局：
**要么今天能跑明天挂**（IP 变了），**要么为了稳定放宽到整个 CDN 网段**
（等于放开了半个互联网，因为那些网段上还托管着无数别的站点）。
**按主机名过滤是唯一稳的做法**，代价是多一个代理进程 —— 这个代价值得付。

### 3.4 白名单变复杂的问题：可控

签字人担心白名单会变复杂。实测上它不会：**白名单的条目数等于「被测系统要调几家模型 API」**，
v1 的主表也就几家。真正会让白名单膨胀的是「让 agent 装依赖」（PyPI、npm、GitHub）——
那应当在**镜像构建期**解决（构建时联网、运行时断网），**不要**放进运行期白名单。

### 3.5 额外收获：代理日志是**证据**

代理日志是网关 `access_log.jsonl` 的**网络侧对应物**。
卡 5.1 的前视探针目前只能在网关日志上结算；有了代理日志，
「这次运行有没有绕过我们的数据面去外面取数」**变成可事后结算的**，
而不是靠「我们相信它没有」。

**这一条把出向策略从「安全措施」升级成「计分证据链的一部分」。**

**2026-09-01 签字确认**：代理日志正式登记为**卡 5.1 前视探针的第二结算源** ——
网关 `access_log` 是**数据面侧**，代理 `egress.jsonl` 是**网络侧**，**两者合起来才覆盖完整**。
只有网关日志时，「绕过数据面」在日志里表现为**什么都没有**，
而「什么都没有」与「这次没取数」**不可区分**。

## 4. ⚠ 一条网络策略**封不住**的前视通道：模型自己的知识截止日期

即使网络完全封死、代理只放模型 API，**仍有一条前视通道**：

> **被测模型的知识截止日期可能晚于我们的冻结线 `2026-07-31`。**
> 若模型「记得」2026 年 8 月的市场发生了什么，那是**权重里的前视**，
> 网络策略、网关日志、代理日志**全都看不见**。

**2026-09-01 签字提级：这不再只是「必须声明的局限」，v1 要把它测出来。**

理由是它威胁的不是单次运行，而是**主表的可比性**：污染程度与模型新旧**正相关**，
新模型看起来更强，可能只是因为它记得更多 2026 年 8 月 —— 这是一个**与被测变量同向**的
系统性偏差，它不会把结果打散，而会把结果**排好序**。

**做法与判据见 `ops/specs/card_3.2_5.1_memory_probes.md`**（题面归卡 3.2，判据与实现归卡 5.1）。
要点：

1. 一组**开放问法**的定向题，问冻结线之后、我们数据面里不存在的市场事实；
2. **控制阶梯**（2025-12 / 2026-03 / 2026-06）—— 没有它，0% 命中无法区分
   「模型干净」与「模型什么都答不出」；控制阶梯顺带给出**实测**知识地平线，
   比厂商声明的 cutoff 可信；
3. 主表加三列：`memory_probe_hit_rate`、`memory_probe_control_rate`、`memory_probe_horizon`；
4. **v1 只报告与标注，不改分**（因此不受 D-04 的前置约束）；
5. 论文的局限一节写「**已测量并报告**」，而不是「无法覆盖」。

**这条对 benchmark 的效力是结构性的**，比任何一条网络规则都更值得写进论文。

## 5. compose lint 的九条规则

拓扑保证**只在 compose 长成那个样子时成立**，所以「compose 长成那个样子」
必须是**可测的**，不能只是笔记里的提醒。实现在 `runner/c41/runner_core.py::lint_compose()`。

| # | 规则 | 依据 |
| --- | --- | --- |
| L-1 | 不得有裸端口映射 `PORT:PORT` | D-07 |
| L-2 | 端口映射必须绑 `192.168.1.219` | D-07 |
| L-3 | `gb_task` 必须 `internal: true`（**结构化判定**，不是子串匹配）| §3.2 |
| L-4 | 网段避开 `10.42/16`、`10.43/16`、`10.88/16` | NET-1 |
| L-5 | 任务容器只许挂**该次运行自己的 work 目录**；判据是**挂载源与 run dir 精确相等**（经 realpath，卡 4.3 TK-1 收紧） | FS-1 / N-29 / TK-1 |
| L-6 | **v1 任何服务都不得发布端口** | D-07 + D-09 |
| L-7 | 任务服务**只能**接 `gb_task`；代理必须同时接两个网 | §3.2 |
| L-8 | 运行期不得装依赖，不得出现包仓库痕迹 | §3.4 |
| L-9 | `HTTP(S)_PROXY` 指向代理且 `NO_PROXY` 含 `gateway` | D-10 |

**L-6 不是 L-1/L-2 的重复**：一个写成 `192.168.1.219:3128:3128` 的映射**格式完全合规**，
L-1/L-2 都不会响 —— 但它把代理**发布到了 LAN**，而 ufw 只对 LAN 生效、tailnet 走
`ts-input` 链绕过 ufw（D-07），结果是**一台对整个 tailnet 敞开的开放代理**。
负例对照里专门有这一例来证明 L-6 的独立判别力。

**验收方式**：`runner/c41/negctl_lint.py` 的 10 个负例，**每个都必须被它自己那条规则拦下**
（只要求「全红」是不够的：一个负例若因别的规则红，被测的那条规则其实是空的）；
外加一个反向对照（只改注释必须仍绿）。同一组用例进主测试套 `ops/test_c41.py`。
