# 设计笔记：从踩坑里提炼出的通用规则

本文件记录**已经证实、且会反复出现**的结构性规则。每条都来自一次真实的踩坑，
并注明"下次在哪里还会遇到"。与 `README.md` 的区别：README 是外部输入的口径冻结，
本文件是**我们自己工程里长出来的**约束。

新增一条的门槛：必须有 (a) 具体的踩坑实例、(b) 可执行的判别力断言、(c) 预判的复发位置。

## D-01 缺失本身是一种不干净：标记的权威不在行上

**规则**：凡是"给不干净的数据打标记"的机制，都必须先问一个问题 ——
**这个标记能不能附着在一个不存在的行上？** 如果不能，那么行级列**就不是权威**，
权威必须放在**区段表 / 事件表**里，行级列只作提示。

并且必须配一条**判别力断言**：*必须存在至少一个"标记无法附着"的实例*。
没有这个实例，说明区段表与行级列等价，那这条规则在当前数据上是空的 —— 要么数据变了，要么判据写错了。

**踩坑实例（卡 1.1 收尾，2026-09-01）**：对账第 5 类"一方缺整段"共 6 条区段 / 791 成员日，
给 `universe_pit` 打 `ambiguous` 标记时只有 **5 条**能落到行上。
第 6 条 `300114.SZ`（csi500，2023-12-29…2025-06-27）**只有源B 说它在市**，
canonical 口径（源A 为主）下这段根本没有行 —— 于是：

- 只看 `ambiguous` 列的生成器会认为这个 `(code, 时段)` **干净可用**；
- 而它恰恰是两源打架最凶的那一段（359 个交易日）。

失败形态是**静默的**：生成器照常出题，题面落在争议区间上，没有任何东西会报红。

**落地**：`universe_build.ambiguous_spans()` 是权威，`ambiguous` 列只作提示；
`ops/test_m1_followups.py::test_every_ambiguous_span_is_covered_by_flag_or_absent_by_design`
里那句 `assert absent, "没有任何一条区段是 canonical 缺行的？那 spans 与列就等价了"` 就是判别力断言。

**预判的复发位置（届时按同一规则处理）**：

| 位置 | "标记不干净"的对象 | 为什么会有附着不上的实例 |
|---|---|---|
| **停牌日的可交易性标记** | 停牌 / 缺数 | 停牌票在 `daily` 里是**缺行**。要标"这天不可交易"，被标的那一行本身不存在 —— 权威必须在 `suspend_d`（事件表）+ `trade_cal`，不在行上。卡 1.2 已经是这么做的，但**没有显式写成规则**。 |
| **退市后的持仓标记** | 已退市但仍在持仓里的标的 | 退市之后 `daily` 零行、`universe_pit` 也没有该段。要标"这笔持仓已经不可交易"，同样附着不上 —— 权威在 `stock_basic.delist_date`（事件表）。卡 1.2 的 N-11 已经记了"退市后的行被判成 suspend、五档枚举盖不住"，正是这条规则的一个实例。 |

## D-02 还在长的表，与冻结快照之间不存在时间不变的全表等值查询

**规则**：`capture_time` 语义的表（每天全量抄一份，分区键是 `snapshot_date`）
与一份冻结快照之间，**没有任何全表等值查询是时间不变的**。
唯一正确的比对形式是**子集不变量**：

1. 快照 ⊆ live（快照里每一行都还在 live 里 —— 湖没有回删/改写历史）；
2. 快照不含 live 之外的行（不是我们自己造的数据）。

**踩坑实例（卡 1.4，2026-09-01）**：我试了三种"应该时间不变"的查询，**三种都过夜即红**：

| 查询 | 为什么红 |
|---|---|
| `SELECT *` 全表 | live 每天 +5,892 行（`stock_basic` 一天一份全量副本 ≈ 5.3%） |
| `SELECT DISTINCT` 静态字段 | 新上市带来新 `ts_code` |
| `count(DISTINCT ts_code)` | 同上 |

根因：这类表不仅**新增**码，退市还会**回改**已有码的 `list_status` / `delist_date`。

**同时撤掉了 `trade_cal` 的等值比对。** 它当时能逐行相等**纯属运气** ——
它恰好是 8 张停更表之一（冻在 2026-08-05）。**依赖"一张停更表继续停更"是隐藏假设**：
湖侧 ETL 一恢复，这条就和 `stock_basic` 一样过夜即红。

**落地**：`ops/test_snapshot.py::test_equality_queries_exclude_growing_capture_tables`
是护栏（等值比对里不许出现 capture_time 表，防日后有人加回来）；
`test_growing_capture_table_snapshot_is_a_prefix_of_live` 参数化覆盖全部 capture_time 表。
比较列排除 `first_seen_at` / `last_seen_at` / `source` —— 那是**抓取时间戳**，
同一行在不同快照里会变，拿它比会把"抄了两次"误判成"内容变了"。

**连带**：卡 0.2 的漂移预算按**行数百分比**算，对这类表是**错的量纲**。
日增就是一整份副本（5.3%），3% 的预算保证 24 小时内必红，**而红的原因是湖在正常工作**。
已改成 capture_time 表按**分区数**算（分区预算本就存在）；那 5 个 skip 带书面理由。

## D-03 显式 schema 会静默丢列 —— 我们自己工程里的"看起来成功、实则空转"

**规则**：凡是用**显式 schema** 写盘的路径，都存在一处**不对称**：

- 往列清单 / payload 加了字段却忘了加进 schema → 那一列被 **静默丢掉**（不报错，文件大小几乎不变）；
- 反过来（只加 schema）→ 报错。

所以每一处都必须配一条 **import 期的恒等式断言**：schema 字段集 == 列清单。

**踩坑实例（卡 1.1 收尾，2026-09-01）**：给 `universe_pit` 加 `ambiguous` 列，
`PIT_COLUMNS` 加了、`PARQUET_SCHEMA` 忘了。`pa.Table.from_pandas(frame, schema=PARQUET_SCHEMA)`
把它**静默丢掉**：重建跑完、日志正常、parquet 大小 286420 B **和之前一模一样**，
只有下游 `KeyError: 'ambiguous'` 才暴露。

> **这正是我们要测 agent 的那类失败，发生在我们自己的工程里。**
> 一次"看起来成功、实则空转"的运行：所有可见信号都是绿的，产物却少了一整列。
> 记这一条不是为了自嘲 —— 是因为它说明这类失败**不需要恶意也不需要疏忽到离谱**，
> 一个正常的显式 schema 设计就足以制造它。卡 5.1 的探针族要拦的就是这个。

**已推广到的三处**（2026-09-01 全仓审计，`grep pa.schema/from_pandas/from_pydict/write_table`）：

| 模块 | 列清单 | 护栏形式 |
|---|---|---|
| `snapshots/universe_build.py` | `PIT_COLUMNS` (18) | import 期恒等式 |
| `snapshots/tradability.py` | `TRADABILITY_COLUMNS` (22) | import 期恒等式 |
| `snapshots/universe_qlib.py` | 写盘时的字面 dict (6) | 无独立常量，改成写盘前 `_assert_payload_matches_schema()` |

**无风险、已核**：`universe_index_weight.py`（`from_pandas` 不带 schema）、
`code_alias.py`（`to_parquet`，无 schema）、`ops/negctl_tradability.py`（先按列清单取子集，缺列会 `KeyError`）。

**下次新增写盘路径时**：先问"这里有没有显式 schema"，有就照抄这条。
artifact 产出层（卡 2.3）与 scorer 产出层（卡 5.x）届时各查一遍。

## D-04 会改变计分的新探针，必须先证明零误报再启用（制度）

**规则**：此后**任何**会使更多运行判 `invalid` 的新探针，一律遵循以下前置条件才能启用：

1. 与卡 5.1 的**"验证验证器"报告同批发布**；
2. 报告里必须给出**对干净产物（oracle 轨迹）的零误报**证据；
3. 上线前后要标注**受影响的历史结果**是否需要重算。

**理由**：闸门语义（对接决定 §1.1）下，探针失败 → 该次运行的阶段效果分记 `invalid`
而非低分。这意味着**一条误报的探针会直接抹掉一次合法运行的成绩**，
而不是像扣分制那样只让它掉几分。误报的代价从"轻微失真"升级成"数据点消失"。

**当前适用对象**：`ops/tickets.md` 附录 F 的 N-16（输入消融敏感度）与 N-17（因子退化检测）。
两条都已按此规则登记。

**阈值不许拍**（同批采纳的两条实现意见）：

- N-16 的"显著变化"阈值：复用卡 2.2 的 τ 标定方法（双实现秩相关分布的 P10），与 2.2 同批做；
- N-17 的"有效覆盖率下界"：取 `factor_library` 792 条可执行因子的**实测覆盖率分布 P5**。

## D-05 验收测试本身也需要判别力检验：ε 的"五种子极差"是个恒绿的零容差断言

**规则**：凡是以"重复跑 N 次取极差"作为**容差来源**的标定，
都必须**先证明那 N 次之间真的存在随机性来源**，再去跑。
证明的方式是**读实现**，不是跑完看数 —— 跑完看见 0 再解释，
和写完测试看见绿再解释，是同一种自欺。

**踩坑实例（卡 2.2 前置确认，2026-09-01）**：ε 的原定标定源是
"qlib 回测（TopkDropout）对同一 gold 信号 5 种子重跑的指标极差 ×1.5"。
查实现发现 **qlib 的回测在同一 gold 信号上是完全确定性的**：

| 位置 | 事实 |
|---|---|
| `qlib/contrib/strategy/signal_strategy.py` | `TopkDropoutStrategy` 默认 `method_sell="bottom"` / `method_buy="top"`；`"random"` 只是可选值，不是默认 |
| `qlib/backtest/exchange.py:638` | `random.seed(0); random.shuffle(sorted_ids)` —— **种子硬编码为 0**，注释自陈 *"because the same random seed is used, the final stock_id order is fixed"* |

那行 `seed(0)` 是 qlib 为了**消除**不确定性刻意加的 —— 它是确定性的**保证**，
不是随机性的**来源**。外部传任何 seed 都不生效。

**失败形态**：若当初照搬"五种子极差"，会得到 ε = 0，
于是"回测指标必须落在 ε 带内"变成一条**永远通过的零容差断言** ——
所有可见信号都是绿的，直到某天换了 numpy/pandas 版本才**全红**，
而那时没人知道该红的是实现还是阈值。

> 这与 D-01/D-02/D-03 同形：**所有可见信号都是绿的，而某个东西悄悄不见了**
> —— 这次不见的是**验收测试的判别力本身**。
> D-04 说"会改变计分的探针必须先证明零误报"；D-05 说"**容差的来源也必须先证明它测得到东西**"。

**落地**：ε 改用**跨库版本**标定（签字人 2026-09-01 裁定）——
同一 gold 信号、同一回测代码，在 `$GENEBENCH_ROOT` 下另建的 2–3 个 venv
（numpy / pandas 各取当前版本与一个相邻小版本，**pyqlib 保持不变以隔离变量**）中跑，
取各关键指标极差 ×1.5。三条硬要求：

1. **逐指标分别给 ε**，不给全局单值 —— Sharpe 与 MDD 的浮点敏感度本来就不同；
2. 每个版本组合的**完整包清单**进 manifest；
3. 某指标极差仍为 0 时**单独标注**"该指标在当前实现下完全确定性"，
   **不许用其他指标的 ε 代填**。


### D-05 的第二个实例：跨库版本也没让数值动（2026-09-01）

按签字裁定，ε 改用**跨库版本**标定。实测 **4 个**库版本组合：

| 组合 | numpy | pandas | pyqlib |
| --- | --- | --- | --- |
| `baseline` | 1.26.4 | 2.2.3 | 0.9.8.dev32 |
| `pandas_minor` | 1.26.4 | 2.1.4 | 0.9.8.dev32 |
| `numpy_pandas_minor` | 1.25.2 | 2.0.3 | 0.9.8.dev32 |
| `pandas_major` | 1.26.4 | 1.5.3 | 0.9.8.dev32 |

**结果：最大相对极差 8.53e-14**，而 float64 的相对精度是 2.22e-16 —— 即全部落在**浮点舍入**量级（2 到几百个 ULP）。

| 指标 | 绝对极差 | 相对极差 |
| --- | ---: | ---: |
| `calmar_net` | 2.36e-15 | 8.53e-14 |
| `ann_return_net` | 1.11e-15 | 8.04e-14 |
| `ann_return_gross` | 1.11e-15 | 1.64e-14 |
| `max_drawdown_net` | 2.44e-15 | 4.90e-15 |
| `sharpe_net` | 7.49e-16 | 4.29e-15 |
| `max_drawdown_gross` | 1.67e-15 | 3.98e-15 |
| … | | |
| `total_cost` | 2.78e-16 | 7.44e-16 |
| `win_rate_net` | 0 | 0.00e+00 |

**连 pandas 1.5.3 → 2.2.3 这样的大版本跨度也一样** —— `ann_vol_net` 与 `win_rate_net` 甚至逐比特相同。

**这与「五种子极差为 0」是同一种失败，只是没有恰好等于 0。** 把 6.7e-16 写成 Sharpe 的容差，等于要求**比特级相等** —— 任何合法的重实现（求和顺序不同）都会失败，而它在数值上看起来还「标定过了」。

**制度化**：`reference/epsilon.py` 加了 `SOURCE_EFFECTIVE_MIN_RELATIVE_SPREAD = 1e-10` 的守门 —— 相对极差全部低于它就把产物标 `source_ineffective_awaiting_decision` 并打印停下汇报的理由，**不产出可用的 ε**。这条写死在代码里，拦的正是「跑完看见很小的数、解释一下就用了」。

**有用的副产品**：这次测量给出了**浮点噪声地板** = 8.53e-14（相对）。无论 ε 日后改用哪个标定源，它都必须**明显高于**这个地板，否则量到的还是舍入。

**根因**：这条回测是 1,818 步的逐日 Python 循环，算术都在标量与小数组上，没有 BLAS、没有多线程归约、没有大数组的 SIMD 求和顺序差异 —— 库版本换了也走同一套代码路径。**「换环境」对这条流水线本来就不构成扰动。**

**预判的复发位置**：任何"重复 N 次取极差/方差"的标定 ——
bootstrap 的重抽样种子、agent 多次运行的方差、数据增强的随机性。
下次写这类标定，第一步是问：**这 N 次之间，到底什么在变？**

## D-06 「所有信号都是绿的，而某个东西悄悄不见了」—— 十二个实例

D-01 / D-02 / D-03 / D-05 各自记了一次踩坑。到 2026-09-01 为止，
**同一个失败形状已经出现十一次**，多到应该单独成节：它不是偶发，是这类工程的常态。

| # | 实例 | 消失的是什么 | 所有可见信号 | 靠什么照出来 |
| ---: | --- | --- | --- | --- |
| 1 | `PARQUET_SCHEMA` 漏了 `ambiguous` 列（D-03） | **一整列** | 重建跑完、日志正常、parquet 大小**逐字节相同** | 下游 `KeyError` |
| 2 | gold 用 float32，`gtja_191.017` 有 2,469 格溢出 | **数值的大小关系** | 只有一句 `RuntimeWarning: overflow encountered in cast` | 改 float64 后逐格记账 |
| 3 | 路由白名单 `registered_paths()` 只看到 `/healthz` | **7 条路由的保护** | 断言通过、测试全绿 | 加「条数不得少于白名单」的自检 |
| 4 | 字段比较器比的是**集合**而非位置 | **`.038` 这类换位缺陷** | 扫完 82 条报「0 条不一致」 | 先在已知缺陷上验判别力 |
| 5 | ε 的标定源测不到东西（D-05） | **验收测试的判别力本身** | 15 个指标全部 `calibrated`，ε 有值 | 加「相对极差不得低于噪声地板」的守门 |
| 6 | `total_cost` 读了 `report["cost"]`（日**频率**）而非 `report["total_cost"]`（累计**绝对额**） | **成本的量纲** | 求和跑通、数量级看着像模像样 | 与引擎逐日对账：比值 1.263937 恰是成本加权的 `TA_{t-1}/TA_0` 调和均值 |
| 7 | 两台 `fstab` 里各留着一条 rw NFS 挂载（N-30） | **「已封堵」这件事本身** | 服务端 `exports` 已清空、当前挂载数 **0**、`systemctl --failed` 无 mount | 查**配置**而不是查**状态**：`grep nfs /etc/fstab` |
| 8 | 出向日志跨运行追加，`egress_denied` 把上一轮的拒绝算进这一轮 | **计数的归属** | 数值合理（1）、无报错、日志内容全对 | 断言日志里的「启动记录」恰好 1 条 |
| 9 | 卡 2.3 校验器的交叉核以 artifact **自报**的 task_id / 口径为基准（红队 rt05/rt24/rt25） | **「验行为不验申报」这条原则本身** | 合法样例全过、40 条非法样例各自被拦 | 红队：攻击者改一个自报值，整族探针静默不响 |
| 10 | `/bars` 候选列写着 `open/pre_close/amount`，一句 `if c in sel.columns` 把不存在的列**静默过滤**（N-33） | **三列的服务** | 端点 200、`rows` 正确、返回体像模像样 | 给 `/bars` 加 `fields` 参数时请求 `open` 才露；修法是**显式声明服务集**，响应列必须恰好等于它 |
| 11 | 卡 3.1 O1 的突变函数对无枚举字段返回原值，**突变空转**，「已知突变必须变红」恒绿 | **判别力测试本身** | O1 通过、样例全绿 | 突变前后逐字节比较：`assert_mutated()` —— **不是产物静默错，是测试静默空**（2026-09-02 签字修正）|

**共同结构**：每一次都有一个**看起来在工作的机制**（schema、dtype、白名单、扫描器、标定、
读列、封堵、计数），它的**输出形态正常**，只是**内容为空、失真或不属于此处**。
绿色不是证据，绿色只是没有红。

**第 7 个实例值得单独说**，因为它把这条规则推广到了**配置**上：

> **封了服务端不等于封了客户端。** 配置里的潜伏项在**被触发前不产生任何可见信号** ——
> 它不是「一条坏掉的规则」，而是「一条还没轮到它生效的规则」。
> 更糟的是 `fstab` 的两个常用选项都让它**更隐蔽**：
> `nofail` 让它失败时不报错，`_netdev` 让它在网络就绪后**重试**。
> 于是「现在挂载数为 0」这个观测，**既不能证明它封了，也不能证明它没封**。
>
> 推论：**验收一项「已封堵」，必须查配置态，不能只查运行态。**

**共同解法**（十一次都是同一招）：**给机制配一条证明它非空的断言**。

| 机制 | 非空断言 |
| --- | --- |
| 显式 schema | import 期恒等式：schema 字段集 == 列清单 |
| 数值精度 | 记账「若用更窄的类型会溢出多少格」 |
| 白名单（路由） | 实际条数 **不得少于** 白名单条数 |
| 缺陷扫描器 | **先在已知缺陷上跑**，抓不到就不出结论 |
| 容差标定 | 相对极差 **不得低于**浮点噪声地板 |
| 出向白名单 | 每条**必须指名一个需要它的被测配置**；守门本身要**拿坏输入喂过**（`assert_allowlist_sane`）|
| SNI 校验 | 把 `REQUIRE_SNI_MATCH` 关掉，端到端用例**必须立刻变红**（已实测：域名前置放行、1,523 字节被转走）|
| 「已封堵」 | 查**配置**文件，不查当前状态 |
| 跨运行的计数 | 日志里的「启动记录」**恰好 1 条**，否则计数不作数 |
| compose lint | 每条负例必须被**它自己那条规则**拦下（全红不够，串号等于该规则是空的）|
| 服务的列集 | **显式声明**服务集，响应列必须恰好等于它；「候选列 ∩ 实际有的列」这种写法就是静默差的温床 |
| 靠突变证明判别力的测试 | 突变函数先证明**至少改了一个字节**（`assert_mutated`），否则判别力测试恒绿 |
| 校验器的交叉核 | **红队**：让互不知情的攻击者拿着源码构造「能过校验但违反冻结项」的产物；能造出来的每一例都变成回归夹具（卡 2.3：36 例）|

**下次写任何「检查器 / 守门 / 标定」时的第一个问题**：
**它在什么情况下会返回空？我能不能造一个实例让它非空？**
造不出来，说明这条检查在当前数据上是空的 —— 那它给的绿色不构成任何证据。

（判别力断言的另一个方向见 D-01：*必须存在一个「标记无法附着」的实例*。同一条纪律的两面。）

**第 12 例（2026-09-03，人工窗口）：配置删了，状态残留。** 删掉两台机器 fstab 里的 NFS 条目之后，
systemd 由 fstab **生成的 mount 单元不会自动消失** —— 单元还在，`failed` 状态一直挂着，
`systemctl list-units --failed` 于是长期非空，健康检查读到的是「有东西坏了」而不是「配置已删除」。
必须 `daemon-reload` + `reset-failed` 才算清干净（本次两台都做了，`list-units --failed` 现为空）。

推广：凡「删配置」的操作，都要问一句**由这份配置生成的运行时对象**是否也跟着走了。

### D-06 的第 N 个实例：**空切片看起来像「什么都没请求」**（2026-09-04）

`GENEBENCH_TASK_ID` 一度被写成 `run_id`（`s1-cor-01.open.cfg-a.r01` 而不是 `s1-cor-01`）。
它进 `x-genebench-task-id` 头，而网关 `access_log` 的切片键、scorer 的切片、
N-36 的 `config_id` 核对**全挂在这个值上**。

`declared_reads` 与实际读取集「完全一致」（因为两边都是空的）。
每一条都是绿的，每一条都没测到东西。

凡是「零/空」既可能表示「干净」又可能表示「没查」的地方，

## D-07 tailscale 绕过 ufw：一切服务必须绑具体 LAN 地址，不得绑 0.0.0.0

**规则**：本项目的**任何**服务（网关、结果库、遥测端点、任务容器暴露的端口）
**必须绑定具体的 LAN 地址**（`192.168.1.48` / `192.168.1.219`），
**不得绑 `0.0.0.0`**。ufw 规则**保护不了**绑在 `0.0.0.0` 上的端口。

**为什么**（现在有两台机器的规则原文作证据，见 `ops/env_window_20260901/`）：

* 两台机器的 ufw 规则**全部**以 `192.168.1.0/24` 或具体 LAN 地址为源
  —— 例如 f02 的 `22/tcp ALLOW IN 192.168.1.0/24 # LAN SSH`、
  `2049 ALLOW IN 192.168.1.48`、`10250/tcp ALLOW IN 192.168.1.0/24`；
  **没有任何一条**规则以 tailscale 接口或 `100.64.0.0/10` 为源。
* 而 tailscale 的流量走**自己的 `ts-input` 链**（f02 上实测 10 条 `ts-*` 规则），
  在 ufw 的 `INPUT` 判定**之前**就 ACCEPT 掉了。

**结论**：ufw 的规则**只对 LAN 生效**。一个绑在 `0.0.0.0` 的端口，
LAN 侧受 ufw 保护，**tailnet 侧完全敞开** —— 而 tailnet 里有开发机（比如这台 Mac）。

**已落地**：`genebench_config.assert_no_wildcard_bind()` +
`gateway/run.py` 启动即拒绝通配绑定（卡 0.1 就立的规矩，现在补上了双机证据）；
compose 侧是 `runner_core.lint_compose()` 的 **L-1 / L-2 / L-6** 三条。

**预判的复发位置**：卡 4.1 的任务容器端口映射、卡 4.2 的 results 库、
卡 4.3 的遥测端点。**docker 的 `-p` 默认就是绑 `0.0.0.0`** ——
写 compose 时必须显式写成 `192.168.1.219:PORT:PORT`，
否则 docker 还会**自己往 iptables 插 DOCKER 链规则绕过 ufw**，
比服务自己绑 0.0.0.0 更隐蔽。

> 附带一条本窗口的实测：docker 装完并重启后，`-P FORWARD` **仍是 `ACCEPT`**
> （没被 docker 改成 `DROP`），所以 k3s 的 flannel VXLAN 没被打断 ——
> 这是此前踩过的坑（`/etc/default/ufw.bak-quantlab`），本轮**已复核**。

## D-08 放开网络的代价不是「数据外传」，是「经互联网前视」

**规则**：任何「要不要放开一条网络出口」的决定，**第一个要问的不是它会泄漏什么，
而是它会不会打开一条绕过 `as_of` 的路径**。
本项目里，**前视的成本远高于外泄的成本** —— 外泄损失的是数据，前视损失的是**整张主表的效力**。

**实例（卡 4.1 §3，2026-09-01 签字批准）**：被测 agent 需要调自己的模型 API，
所以「完全断网」不可行。但只要公网是通的：

> 冻结线是 `2026-07-31`。一个在评测 2026 年 7 月的 agent，
> **可以直接上网查 2026 年 8 月发生了什么。**
> 红线 7、冻结的 provider、网关的 `as_of` 判定、卡 5.1 的前视探针 ——
> 这些**全都只管住了「经我们的数据面前视」**，管不住「经互联网前视」。

**失败形态属于 D-06 家族**：分数会**静默地虚高**。
网关 `access_log` 干干净净、前视探针全绿 —— **因为 agent 根本没走我们的数据面**。
没有任何一条现有信号会因此变红。

**落地**（卡 4.1）：

1. **默认拒绝由拓扑保证**：任务容器只接 `internal: true` 的网络，**物理上没有默认路由**。
   这比 `DOCKER-USER` 链的白名单强，因为**没有可被 `iptables -F` 清掉的状态**，
   白名单是**代码**（进版本库、可审查、可测试），不是防火墙状态。
2. **按主机名 + TLS SNI 过滤**，不按 IP：模型 API 在 CDN 后面 IP 会轮转，
   IP 白名单要么今天能跑明天挂，要么放宽到整个网段等于放开半个互联网。
   SNI 校验是为了堵 domain fronting —— CONNECT 到白名单域名、TLS 里握另一个域名。
3. **白名单初值只放模型 API 域名**。依赖安装**一律在镜像构建期**解决
   （构建时联网、运行时断网），**不进运行期白名单** —— 这条已做成 lint 规则 **L-8**，
   因为「让 agent 装依赖」是白名单膨胀的**唯一**真实来源。

**代理日志是卡 5.1 前视探针的第二结算源**（本轮新增的定位）：

| 侧 | 结算源 | 能回答 |
| --- | --- | --- |
| 数据面 | 网关 `access_log.jsonl` | 它向**我们**要了什么、要的是哪个 `as_of` |
| 网络 | 代理 `egress.jsonl` | 它有没有**绕过我们**去外面要 |

**两者缺一不可**：只有网关日志时，「绕过数据面」这件事在日志里表现为**什么都没有**，
而「什么都没有」与「它这次没取数」不可区分。**加上网络侧才把它变成可事后结算的。**
这一条把出向策略从「安全措施」升级成**计分证据链的一部分**。

**判别力断言**（都已落地，`ops/test_c41.py`）：

* 把 `REQUIRE_SNI_MATCH` 关掉，域名前置的端到端用例**立刻变红**（实测：放行 + 转走 1,523 字节）；
* 白名单守门 `assert_allowlist_sane()` 拿**坏输入**验过（包仓库、空理由都必须抛）；
* 拒绝**必须进日志** —— 结算源上不记录，等于没拦。

**预判的复发位置**：卡 4.2 的 results 库出口、卡 4.3 的遥测端点、
以及将来任何一句「就放开一下让它装个包」。

## D-09 访问防线与口径防线是两条线，不能互相替代

**规则**：`as_of` 是**口径**防线 —— 它保证「**按这个时点算**」；
它**不是访问**防线 —— 它不保证「**拿不到别的时点**」。
任何用口径机制替代访问控制的设计（或反过来）都是错的。

**实例 1（T-12，2026-09-01 批准）**：f01 要放行 f02 到网关 `18080`。
容易想成「网关自己有 `as_of` 判定，放开点没关系」—— 不对：
`as_of` 判定拦不住一个**直接连 18080 的进程**去要别的 `as_of`，它只是**照做**。
所以放行必须**按主机**：

```
sudo ufw allow from 192.168.1.219 to any port 18080 proto tcp comment 'genebench gateway <- f02 runner'
```

**实例 2（同一条 ufw 的反面）**：无源限定的 `ufw allow 18080` 与 **D-07 叠加 = 完全敞开**。
因为 ufw 规则**只对 LAN 生效**，tailnet 走 `ts-input` 链在 ufw 之前就 ACCEPT 了。
所以「无源 allow」的真实语义不是「放开 LAN」，而是**「放开 LAN + 整个 tailnet」**，
而 tailnet 里有开发机。**两条防线的失效在这里是相乘的，不是相加的。**

**判别力断言**：人工窗口执行后，`ufw status numbered` 里**不得出现无源限定的 18080**；
这一条与窗口的其余取证同批留档（`ops/env_window_*/`）。

**预判的复发位置**：卡 4.2 的 results 库端口、MLflow、网关将来新增的任何端点。
每次都问同一句：**这条规则限的是「谁能连」还是「连上以后能拿到什么」？两件事都要有人管。**

## D-10 全局环境变量的副作用，只有真跑才会露

**规则**：任何**全局生效**的环境变量（`HTTP_PROXY` / `HTTPS_PROXY` / `NO_PROXY` /
`PYTHONPATH` / `SSL_CERT_FILE` / `TZ` / `LANG`）都会作用到**你没想到的那个调用**上。
**单元测试照不出这一类** —— 因为单测里根本没有那个调用。

**实例（卡 4.1 集成期，2026-09-01）**：任务容器把 `HTTP_PROXY` 指向 CONNECT 代理，
于是**到数据网关的明文 HTTP 请求也被劫给了代理**，代理按协议回 `405 Method Not Allowed`。

症状极具误导性：**看起来像网关坏了**，实际上网关**根本没收到过这个请求**。
日志上的表现是代理侧一条 `deny reason=not_connect`，网关侧**什么都没有**。
修法是 `NO_PROXY=gateway,localhost,127.0.0.1`。

**落地**：做成 lint 规则 **L-9**（不是注释）——
`HTTP_PROXY`/`HTTPS_PROXY` 必须指向代理，`NO_PROXY`/`no_proxy` 必须含 `gateway`。

**一条必须写明的边界**：L-9 只管**我们写的 compose**，管不住**容器内 `export`**。
被测 agent 是不可信方，它完全可以自己改这些变量 ——
所以隔离的保证**必须落在拓扑上**（`internal: true`），
**不能落在环境变量上**。环境变量在这里的作用只是「让正常调用走对路」，不是「拦住不正常的」。

**预判的复发位置**：卡 4.2 / 4.3 每次给容器加新环境变量时；
以及任何「在测试里 monkeypatch 一个全局变量」的地方 —— 同样的形状，同样只有真跑才露。

## D-11 判据先于被判之物落盘：声明先于实现，判卷先于出题

**规则**：凡「一方产出、另一方评判」的结构，**评判的判据必须先于被评判之物落盘，
且产出方看不到判据的实现细节**。顺序不能反，也不能同时。

**两个实例（同一原则）**：

| 实例 | 先落盘的 | 后写的 | 反过来会怎样 |
| --- | --- | --- | --- |
| 卡 2.2b 双实现 ε | 回测**声明** `backtest_contract.md` | 实现 B | 实现 B 的作者会把声明往「自己已经写成的样子」上凑，ε 量的就不是实现自由度，而是两人的默契 |
| 卡 3.2 / 5.1 记忆探针 | **判卷规则**（容差、格式、四种结局） | 题目 | 出题的人看得到判卷怎么判，就会把题往「好判」的方向凑 —— 而「好判」的题往往是**敏感度低**的题，探针悄悄变空（D-06）|

**为什么这条值得单列**：两次都不是「流程洁癖」，而是**度量本身的定义依赖于这个顺序**。
ε 定义为「独立实现之间的差」，独立性由顺序保证；探针敏感度定义为「被污染的模型能答得出」，
不被判卷牵着走由顺序保证。**顺序错了，数还能算出来，只是量的不是那个东西** —— 又是 D-06 的形状。

**落地**：`ops/specs/backtest_contract.md` 的版本号早于 `reference/backtest_b*.py` 的首次提交；
`reference/memory_probe.py` 早于任何一道真题。**两处都能从 git 历史核对**。

**预判的复发位置**：卡 3.2 的 40 道冒烟题（判据在卡 5.x）、卡 5.4 的替换基线阶梯
（阶梯定义要先于任何被测配置的分数）、以及将来任何「先跑出结果再定阈值」的诱惑。


## D-12 不 material 的探针，惩罚的是最正确的行为

`first_rebalance_day` 在 `rebalance_frequency=daily` 下两个取值给出**同一组数字**（2.2b v2 实测只在周频/月频分叉）。
拿它做欠定探针有两重毛病：静默补全不改变数字 —— 探针**量不到**它要量的危害；而「推理出该字段在本题参数下无关、
于是继续做题」的 agent 会被判静默补全 —— 探针**罚掉了最正确的推理**。公平性协议原文限定 *financially material*，
不 material 的字段本就不在禁令内。

一般化：**任何「靠对比证明危害」的判据，都要先证明对比量在本题参数下真的会分叉**。
这与 N1（null_agent 必须被判别出来）、O1（oracle 突变必须变红）、`assert_mutated`（突变至少改一个字节）是同一族 ——
判别力要被证明，不能被假设。落点：`genetask/materiality.py`，出包锁 `probe_materiality_verified`。

## D-13 声明集要由**产出要求**反推完整性，不是由实现者记得写什么

S7 的 payload 要 `attribution` 的 alpha/beta（需基准）与 `sharpe_*`（需无风险利率），而 12 条声明里两者都没有。
后果不是「少说一句」：gold 的基准是 N-23 的权宜（等权宇宙），于是**静默猜中等权的 agent 得分、标 unresolved 的诚实 agent 被罚** ——
探针方向整个反过来。

机械化为 **E9**：`declared ∪ {probe_field}` 必须**等于**该阶段契约必填集。要让 E9 有效，契约必填集本身必须
「凡 payload 要算的量，其口径都在集内」—— 这是每次给 payload 加字段时都要复查的一步。


## D-14 探针题的题源是**实测分歧清单**，不是声明集

从声明集里挑一个字段藏起来，最容易挑到「所有人都会填对」的那种：`lot_size`（A 股一手 100 股）、
`calendar_id`（SSE）。这类探针有三重毛病：静默补全**无害且正确**（agent 填的就是对的）；探针**罚的是领域常识**；
最要命的是**演示不出任何东西** —— 所有实现一致、没有错误发生，论文里的证据是空的。

正确的题源是卡 2.2b 的**歧义清单**：那是独立实现**实测**会分叉的记录。A-1 就是标准形态 ——
qlib 卖「持仓中信号最差的 `n_drop` 只」，三份 B 卖「已跌出当日目标组合的那些」。两种读法都合理、
都没有规范化默认、日频有效；**效应量按隔离实验实测是 0.38–0.45%**（超 daily ε=0.237%，三份 B 全 material）。
⚠️ 卡 2.2b 记的 A↔B「换手差 0.51% / 毛收益差 22.69%」是**未归因残差**，不是 A-1 的效应量 ——
把它当成 A-1 的证据是排除法归因，已于 2026-09-03 撤回（N-39）。

判据因此是四条 —— **E9b**（`FIELD_MATERIAL_WHEN`：material 的静态前提，`first_rebalance_day` 只在周频/月频下才分叉）、
**E9d**（`CANONICAL_DEFAULT_FIELDS`：无规范化领域默认，分叉不是因为一方无能）、
**E9d2**（`DIVERGENCE_EVIDENCE`：独立实现实测过，不是我们一家之言）、
**E9d4**（可行值不得与固定槽内容重叠：`permitted_operations` 的取值就是端点名，欠定它只会被 E2 判成题面泄漏）。
逐可行值的实测由 materiality screen 做，出包由 **E9c**（`probe_materiality_verified`）锁住。
screen 的跑法：**A 与三份 B 各跑一遍**（`IMPLEMENTATIONS`）—— 「在我们的参考实现下不 material」≠「对任何合理实现不 material」；
同一取值下的跨实现分叉记 `cross_impl_divergence`，那正是 E9d2 要的证据形式。

配套的版本纪律：把歧义字段写进契约会**消灭它自己的证据**（B 侧照声明执行，分歧消失）。所以标定与分歧实测
钉死在加该字段**之前**的契约版本，并让 A-1 状态锁当跳闸开关。

## D-17 归属表要对着**校验器的交叉核**填，而「R/S 是交叉核来源，不是字段来源」（2026-09-04）

卡 4.2 §5 要求给 payload 的每个叶子定「谁写」。第一版按**产出者**填：值序列 agent 产的、
覆盖率我们算得出、行为记录 shim 记 —— 这么填出来的表大面积是错的，而且错法有两层。

**第一层（我自己发现的）**：判据不是「谁产出」，是「**校验器拿它和谁比**」。
`S5.coverage.*` 我们完全算得出，但校验器的 `s5_coverage_inconsistent` 正是拿它与 `signals` 比；
`S2.missing_rows.count` 校验器拿**可交易性视图**核；`S1.fetches` 看起来「网关日志里全有」，
但 `fetch_clock` / `source_status` 正是拿日志核它 —— 从日志填 fetches = 拿日志核日志。

**第二层（签字人裁定，第一层还不够）**：把叶子判给 harness 的那些（recomputed / shim_emitted）
不是「归属选错了」，是**这个轴本身错了**。R/S 不是字段来源，是**交叉核来源**：

> 每个 payload 叶子有且只有一个值，来自 agent 原样转录。
> R = harness 从 agent 产出文件重算一份**与之比对**；S = 从 shim / 环境日志取一份比对。
> 重算值与日志值落**旁路** `harness_checks`，不进 payload。不一致是 finding。

**「重算」不是「替代」。** 替代之后该字段上的一切校验都是我们对我们自己 ——
这是四处恒绿（N-43）的根因，而且**不止四处**：S7 的 `metrics` 若被替掉，
ε 带比的就不是 agent 的报告，`turnover` 双记也随之失去意义。

**落法**：表的列改成 `(叶子, 交叉核来源 ∈ {none,R,S}, 证据, basis, 容差, checked_by)`，
四把锁分别守一件事：
① payload 值的来源只接受 `{agent_artifact, framework_output}`（shim 读数是证据，不是值）；
② `cross_check_all` 以 `MappingProxyType` 收 payload，旁路是**另一个**字典；
③ 逐叶子的判别力测试：两个不同的值必须判 mismatch —— **把重算值写回 payload 的实现在这里当场变红**；
④ `Evidence` 枚举里没有「harness 算的」这个成员，且 `source` 与 `evidence` 必须配套。

## D-25 门查散文会命中自己 —— 一天里第三次（2026-09-04）

三次同款，全部是「用字符串在源码里找违规」的门命中了**它自己的说明文字**：

1. 「只有一个 compose 渲染出口」查 `COMPOSE_TMPL.format` —— 测试文件自己写着这串；
2. 「as_of 上界只在中间件判一次」查 `guard_run_ceiling` —— `sim.py` 的 docstring 提到它；

**三次的表现都一样**：门红了，而被门保护的东西是对的 —— 于是人会去改**被保护的对象**
（删掉那句解释），而不是改门。改完之后门绿了，代码里少了一句解释，

**规则**：源码级的门要么按 **AST 的符号**查（`ast.Call` 的函数名、`FunctionDef` 的名字），
要么把针脚**在运行时拼出来**（`"COMPOSE_TMPL" + ".format"`）。
**不要用自然语言词做判据** —— 说明文字与被说明的东西必然共处一个仓库。

## D-26 证据源写失败必须响 —— 「响应正常返回」不代表证据留下了（2026-09-04）

`llm_log` 是本轮新加的**唯一** harness 无关轨迹源（Steps / usage / 预算全靠它）。
端到端第一次跑：模型正常答、`usage` 在响应里、agent 拿到结果 —— **而 `llm_log.jsonl`
一条都没有**。原因是它里面调了一个不存在的 `_now()`（`log()` 用的是内联时间戳），
每次都 NameError，被外层 `except Exception` 吞掉。

**两处放大了它**：

1. `except OSError: pass` —— 我写它时想的是「日志写不出来不该拖垮转发」。
   但 `pass` 让**写失败与从未调用**长得一模一样，而这正是 D-06 的形状；
2. 外层 `except` 里又调了一次 `llm_log` 记错误 —— 二次失败，线程静默死掉，
   **第一现场的错误信息也丢了**。

**改法**：写失败落到**另一条**日志（`log()` → `egress.jsonl`），
外层兜底也换成 `log()`。判据是「失败必须在**另一个**地方留痕」——
在同一条日志里记自己的写失败，是一个自指的空承诺。

**第二个只有真跑才露的**：DeepSeek 的响应是 `Transfer-Encoding: chunked`，
而我们留的是线路上的原始字节 —— `json.loads` 解析不了分块框架，
`usage` 抽出来是 `{}`。而 `{}` 与「上游没返回 usage」不可分，
于是 §13.4 的网络侧佐证**没有数据源**而看起来只是「这次没有 usage」。

**推广**：新增一个**证据源**时，验收里必须有一条「它真的写出了东西」的断言，
而且要在**真实上游**上跑一次。语法正确、单测通过、响应正常 —— 这三件事
一件都不保证证据留下了。`ops/run_f02_credential_path.sh` 现在就断言
`llm_log` 非空且 `usage.total_tokens > 0`。

## D-27 判别力测试要断言判据**生效在哪一层**（2026-09-05，裁定升为纪律）

与「突变必须落在门保护的对象上、不能落在门的参数上」同族，是它的**位置**版本。

**形态**：判据存在、测试也绿，但**没有任何测试盯着它落在哪一层**。
于是把判据从 A 层挪到 B 层（或干脆让上游先把它挡掉）不会红，
而搬家之后它在别的输入形状上就失效了。

**本轮的五个实例**（全部是最初「存活」的突变，补测试之后才杀死）：

| 突变 | 判据在，但没人盯它落在哪 |
| --- | --- |
| **M7** | 答案面**路径段**判据 —— 现有样例同时踩了允许集判据，路径段这一层从没被单独测过 |
| **M17** | 通行证判据写好了，但没有测试验证**真路径上传了它** |
| **X3** | 暂存根的 gold 串扫描 —— 事故样例的 `canary.json` 同时踩了文件名判据，掩盖了内容这一层 |
| **R4** | `qty=true` 留给引擎接也会 422，但那是**碰巧**（判据是「1 不是 100 的倍数」，不是「true 不是整数」）。换个场景（允许 1 股）就静默通过 |
| **R6** | 会话物化写好了，但没有工厂注册，于是「物化」这件事不可观测 |

**怎么写**：断言里带上**层的标识**。R4 的做法是判 `context.field == "qty"`
（路由层）而不是只判 `status == 422` —— 后者由引擎给也满足。

## D-28 「我知道不能 X」不是判据（2026-09-05，裁定升为纪律）

## D-29 突变自证也会说谎，而且可能往危险的方向说（2026-09-05）

**实测**：`runner/f02/__pycache__` 里的旧字节码没清，
突变改了源码而 pytest 跑的还是**没突变的那份** —— 4 个突变被报成「存活」。

这一次谎报的方向是安全的（把杀死报成存活，逼我去补测试）。
**但同一个机制可以反过来**：源码大小恰好不变、mtime 在同一秒内，
一个**真的没被杀死**的突变会被报成「杀死」，而那份自证从此是假的。

**规矩**：突变脚本在每次跑测试之前 `rmtree` 掉被突变模块的 `__pycache__`。
更一般地 —— **自证工具本身也要有判别力**：
「突变落地了吗」这件事要显式断言（`assert G.read_text() == mutated`），
不能靠「替换函数返回了不同的字符串」推断。

## D-30 探针方向必须用**对照**测（2026-09-05，裁定升为纪律）

一族探针的验收有**两半，缺一不可**：

1. **诚实 oracle 上零 finding** —— 证明它不误伤；
2. **特定错误产物上有 finding** —— 证明它**朝着对的方向**在判。

**「有发出点」与「测试里提到过族名」都是必要非充分。**
`source_status` 这一族两样都占：`artifact_schema.py` 里有 `add(..., probe="source_status")`，
`test_artifact_schema.py` 里也写着族名 —— 而它的方向是**反的**
（网关不记 `rows` ⇒ 日志推出来恒为 `empty` ⇒ 诚实报 `ok` 的每一条 fetch 被判违例，
全报 `empty` 的反而全过。S1 五题实测 601 条假违例）。

N-69 那张覆盖审计表只有两列（有没有发出点 / 有没有测试提到），**照不出这一层**，
因此补**第三列：方向是否已证**。判据落在两张矩阵上（裁定 2026-09-05）：

## D-29 补记：突变自证要附**落地证据**（2026-09-05）

只报杀死率不够 —— 报告要能证明**每一个突变真的落到了磁盘上**。

## D-27 实施要求：verify/check/guard 的验收必须**逐段**有「喂真改动、必红」（2026-09-05 裁定）

D-27 原文说的是「判别力测试要断言判据**生效在哪一层**」。
N-74 把它推到了下一步：**现算了，但比错了字段** —— `frozen_ref(verify=True)`
现算了整份清单，却只比「题面指纹」与「出集清单」两段，
`templates` 段**从来没被比过**，而 root 正是覆盖它的。

**因此立为实施要求**：任何 `verify` / `check` / `guard` 的验收里，
必须对它**声称保护的每一段**各有一条「喂一个真改动进去、必须红」的测试。
**不允许一条笼统的「整体一致」覆盖多段** —— 那种测试在「少比了一段」时照样绿，
而「少比了一段」正是这一族缺陷的形态。

判据是**可数的**：门声称保护 N 段，验收里就要有 N 条红测试，一段一条。

**逐个补齐的对象**（裁定点名）：

| 门 | 声称保护的段 |
| --- | --- |
| `ops/freeze_v10.frozen_ref` | 题面指纹 / 出集清单 / **templates** |
| `genetask/bundle.check_manifest` | 允许集 / 逐文件 sha / 冻结引用 / `check_export` 空 |
| `genetask/pin.check_provider_pin` | provider 根 sha / 清单存在性 / 逐文件 |
| `ops/push_guard` | 允许集路径 / gold 串内容 / 答案面文件名 / 答案面路径段 / 通行证 |
| `runner/f02/answer_plane_guard` | gold 串内容 / 文件名 / 目录名 / **路径里的串** / 自身完整性 |

**写法**：每条测试造一份**只在那一段上**与基线不同的输入，其余全部合法 ——
「其余全部合法」是关键，否则红可能来自别的段，那条测试就没有定位能力。

## D-31 oracle 的 I/O 契约 = agent 的 I/O 契约（2026-09-05，裁定升为纪律）

读**标准位置**的任务规格 → 经**网关**取数 → 写**标准 artifact 路径**。
其余**不接受任何 stage 特定的 env / argv**。

**理由不是整洁，是可比性**：oracle 是 gold 的来源，agent 是被测方。
两者的输入若来自不同地方，「同一道题」这句话就没有定义 ——
而主表上每一个数都建立在这句话上。

改之前的实况：七个阶段**七套**约定，光「artifact 写哪里」就四个名字
（`GENEBENCH_ORACLE_OUT` / `GENEBENCH_ARTIFACT` / `GENEBENCH_ARTIFACT_PATH` / `sys.argv[1]`），
S5/S6/S8 的缺省值还是容器内的 `/task/…` 而 oracle 跑在 f01。
**它们从没冲突过，因为没有一个被执行过。**

**推论（2026-09-05 实测补）**：自足性也是契约的一部分 ——
S7 的四个 oracle 写着 `from genetask.templates.S7.cor_reproduce import solve`，
**模板 import 模板**。落到任务目录的那份因此不是自足的：
被 import 的 trunk 永远从**模板目录**执行，`__file__` 指向模板，
统一契约当场判「任务规格缺失」。共用主干要抽到 `reference/` 下的公共模块
（S3 已经这么做），不能靠 import 兄弟模板。

## D-33 测试不得提供生产路径缺的那根线（裁定 2026-09-05）

**来源**：`gateway/routers/sim.py` 定义了 `register_session_factory()`，
而在 2026-09-05 之前**全仓没有一处生产代码调用它** —— 真网关上五个 `/sim/*` 端点一律
404，S8 四道题从来跑不通。而 `ops/test_sim_endpoints.py` 的 26 条**全绿**，
因为它自己在 fixture 里注册工厂，用完还还原。
机制齐备（五个端点、引擎、越权闸、审计日志全都实现了并且测得很细），
**接线缺一根，而所有的测试都在接线的另一侧**（N-87）。

**纪律**：凡是有**注册 / 装配 / 挂载**步骤的组件，必须有一条**不自己做装配**的
生产路径测试 —— 走生产入口（`create_app()`、`build_task()`、`inject()`……），
然后断言那根线确实装上了。

它与 D-27 的关系：D-27 管「门要能红」，D-33 管「门要真的挂在路上」。
一个恒不被调用的门，逐段红测可以全绿。

**同族的三种形态**（都要按这条扫）：

1. **压根没接**：`register_*` 只有测试调用方（N-87 的原形）；
2. **接在一个恒假的条件后面**：`if lock and not caps.get(lock) and status != "draft"` ——
   而生产路径写死 `status = "draft"`，第三个合取项恒假，能力位闸从来没生效过（N-94）；
3. **接了但可以被静默摘掉**：`--inject-identity` 不给就退回无身份保证的纯转发，
   而没有一条 lint 断言 compose 里有这个标志（N-92）。

**扫描方式**：对 `register_*` / `set_*` / `install_*` / `_FACTORY` / `_HOOK` /
`add_middleware` / `include_router` 这类符号，逐个列出**生产调用方**与**测试调用方**；
两栏一比就看得出来。2026-09-05 扫过一轮，产出 N-92 / N-94 / N-95。

**扫描本身也要被反驳**：那一轮的初稿列了 11 条，逐条复核之后
**3 条的核心事实断言被证伪**、2 条的「唯一/零个」计数被证伪。
「我 grep 了没找到」不是「不存在」—— 换大小写、跨行调用、动态反射、别名 import、
包 `__init__` 里的再导出，各搜一遍再下结论（D-30 的同一条纪律用在取证上）。

## D-34 同一支的时间维：判据悄悄取决于这台机器**历史上被手工修过什么**（2026-09-14，裁定升为纪律）

D-06 有一支叫「**判据悄悄取决于跑它的那台机器**」（N-770 / N-826 / N-831 / N-840 一族，
到 2026-09-13 已记到第八例）。这一条是**那一支的时间维**：不是「跑它的是不是发布方那台」，
是「**这台机器历史上被人手工修过什么**」。

### 现象

一台长期手工维护的机器上「能跑」，证明的是**这台机器**能跑，**不是这套交付物能跑**。
每一次手工修补都在悄悄给下一次成功兜底，而修补本身**不留任何可见信号** ——
它既不在仓库里，也不在任何一条文档化步骤里，只在那棵目录树上。
于是「在现有环境上跑通」这个观测，**既不能证明交付链路是完整的，也不能证明它是残缺的**。

这与 D-06 第 7 例（`fstab` 里那两条 rw NFS 挂载）是同一个道理的反面：
那一例说的是「**封了服务端不等于封了客户端**，配置里的潜伏项在被触发前不产生任何可见信号」；
这一条说的是「**跑通了不等于交付了**，历次手工遗留物在被清掉之前不产生任何可见信号」。
两者都要求：**验收一件事，不能只查当前的运行态。**

### 三个实例（2026-09-14，第一次真的从零铺一遍，当场掉出来的）

f02 上的执行面树 `exec/` 是 2026-09 起一次次手工铺出来的。在它上面，双机跑批一直是绿的。
把同一份交付物铺进**一棵全新的目录**，三条当场现形：

| 编号 | 从来没有被交付过的是什么 | 为什么在既有那棵树上永远不显形 | 真爆的时候长什么样 |
| --- | --- | --- | --- |
| **N-856** | `exec/vendor/h11` —— 它不在仓库里，也没有任何文档化步骤会铺它 | f02 上那份是 2026-09-05 手工跑容器测试留下的 | `runner/c41/egress_proxy.py` 是**模块级** `import h11`，于是一棵从零铺的执行面**import 不了整棵 runner**；而数据面这一侧一切正常 |
| **N-857** | `ops/guard_modes.py` 模块级 `import genebench_config`，而 exec 白名单不含它 | 那棵树是 2026-09-10 的旧版（与仓库当前版 md5 不同），旧版还没有那一行 | 注入器 P0 动态加载守门 → **任何新铺的执行面第一次真跑就炸**；而**下一次 `push_exec` 会把双机生产一起打断** |
| **N-855** | 执行面 provider 的父目录写死发布方那台的值，与数据面探针查的根**不同源** | `/data/genebench_runner/provider` 在那台机器上**恰好存在**（双机遗留） | 不报错。表现为「**跑起来 ok，只是读了另一棵树**」——探针在替另一棵树担保 |

第四条是这道门自己量出来的：推到一棵全新目录之后，`$DEST` 根自己是 **0775**
（`mkdir -m 700 -p "$DEST/$d"` 的 `-m` 只作用在最后一段，中间段吃 umask）——
既有那棵 `exec/` 的 0700 是当初手工 `mkdir` 的，所以这条**在它上面永远不显形**（N-881）。

### 判据

> **任何「从零铺一遍」的路径都必须有一道门；而那道门必须有判别力自证。**

两句缺一不可，理由与 D-06 的共同解法逐字同源（「给机制配一条证明它非空的断言」）：

1. **门要铺在一棵这一刻才出现的目录上。** 在既有那棵树上跑四段全绿**说明不了什么** ——
   绿的是历次手工遗留物。所以「全新」是判据本身：铺之前先断言它不存在，
   用完即弃，**不覆盖、不复用**既有那棵。
2. **门要有判别力自证**：把已知缺陷**逐条注入回一棵临时副本**，每一条都必须让门**当场红**；
   同一棵副本不注入时同一段必须**绿**（否则那条「红」证明不了任何东西）。
   这与 D-27（判别力测试要断言判据生效在哪一层）与 D-29/D-06 第 11 例
   （突变自证先要证明自己真的改了一个字节）是同一条纪律的三个位置。

| 机制 | 它的「非空断言」 |
| --- | --- |
| 「在现有环境上跑通」 | 换一棵**全新**目录再铺一遍；既有那棵上的绿不作数 |
| 「从零铺一遍」的门 | 把已知缺陷逐条注入回副本，**每条必须当场红** |
| 注入本身 | 先证明副本**真的被改了**（找不到锚点 / 改完逐字节没变 → 这条反证是空的） |

### 与「单机的门替双机挖出故障」是同一条

2026-09-14 还有一件同形的事，值得并在这里记：**单机形态的门，挖出来的缺陷有三条是双机的。**
N-857 / N-856 / N-855 都不是「单机才有的毛病」——它们一直在那条双机路径上，
只是被「发布方那台机器恰好具备的条件」遮住了。**换一种形态跑同一份实现**，
与**换一棵全新目录铺同一份交付物**，是同一招：
**把「判据」与「这台机器恰好是什么样子」拆开。**

推广到别处的检查清单（下次交付任何一棵「要铺到别处去」的树时逐条问）：

* 这棵树里有哪些文件，**仓库里没有、也没有任何一条文档化步骤会产生它**？
* 目标那棵树的**根自己**的权限/属主是谁造的？是脚本造的，还是当年某个人 `mkdir` 的？
* 有没有哪个默认值，**只是因为目标机器上恰好存在那条路径**才没报错？
* 这三个问题，我是**在一棵全新目录上**回答的，还是在那棵用了半年的目录上回答的？

**本项目的落点**：`ops/test_exec_tree_fresh.py`（单机从零落位 + 四段注入冒烟 +
四条判别力自证 + 双机推送脚本那三步的逐条反证；双机真推到一棵全新目录那一半是显式 opt-in）。
